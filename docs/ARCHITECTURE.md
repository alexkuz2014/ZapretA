# ZapretA: архитектура MVP

Статус: исследовательская версия, этап 0. Проверена ветка `main` Flowseal `zapret-discord-youtube` (скачанная в ходе исследования); upstream-каталог изменяемый, поэтому перед реализацией нужно зафиксировать commit SHA и повторить сверку.

## 1. Модель стратегий Flowseal

Все найденные `general*.bat` используют общий каркас запуска `winws.exe`: `--wf-tcp`/`--wf-udp` выбирают перехватываемые порты, а последовательность блоков `--filter-* ... --new` задаёт независимые правила фильтрации и десинхронизации. Общие списки: `list-general.txt` (+ user), `list-exclude.txt` (+ user), `ipset-all.txt`, `ipset-exclude.txt` (+ user), отдельный `list-google.txt`; `discord.media` задан напрямую в части профилей. UDP/443 — QUIC fake; Discord voice/STUN — отдельные диапазоны UDP и L7-фильтр. TCP правила обычно охватывают 80/443, отдельные альтернативные HTTPS-порты 2053/2083/2087/2096/8443, и дополнительный Game Filter.

В таблице сокращения: **F**=`fake`; **FS**=`fake,fakedsplit`; **MS**=`fake,multisplit`; **MDO**=`fake,multidisorder`; **HD**=`hostfakesplit`; **SD**=`syndata`; **MDI**=`multidisorder`. Значения относятся к наблюдаемым конфигам, не гарантируют одинаковый эффект на всех сетях. У каждой стратегии обычно разные режимы по отдельным фильтрам внутри одного профиля.

### Нормализованная модель

Хранить **упорядоченный набор правил**, не плоский набор флагов профиля:

```text
StrategyCatalog { schema_version, engine_version, source_revision, strategies[] }
Strategy { id, label, provenance, risk, rules[] }
Rule {
  transport: TCP | UDP,
  destination_ports[], l7_protocols?,
  hostlists[], hostlist_excludes[], ipsets[], ipset_excludes[],
  desync_methods[], repeats?, fooling?, cutoff?,
  split_position?, split_sequence_overlap?, split_pattern?,
  fake_payloads: [{ kind, relative_path, sha256 }],
  extra_supported_arguments[]
}
```

Разделить `--wf-*` (широкий перехват) и `--filter-*` (правило обработки). Сохранить исходный argv и commit источника для аудита и точного сравнения; построение argv должно быть типизированным и проверять пути/хеши файлов. Не генерировать строки командной оболочки и не запускать через `cmd.exe`.

## 2. Выбор движка

| Вариант | Сильные стороны | Ограничения и риски |
|---|---|---|
| A. Rust-оркестратор + upstream `winws.exe`/WinDivert | Быстрее до работающего MVP; переносит проверенные upstream-алгоритмы; стратегии задаются аргументами; Rust отвечает за диагностику, перебор, UI, кэш и жизненный цикл. | Поставляются native EXE/DLL/SYS; итоговый продукт не является одним физическим EXE, если зависимости реально не вшиты/не распаковываются; driver должен быть подлинным и совместимым с Windows security policy; бинарники увеличивают размер и AV-эвристики; лицензии/хеши/версии каждого артефакта надо фиксировать; subprocess cleanup и конфликтующие экземпляры требуют надёжного контроля. |
| B. Собственный Rust engine + WinDivert API | Больше контроля над обработкой, телеметрией и жизненным циклом; меньше зависимости от CLI и можно реализовать только нужные стратегии. | Высокая стоимость и риск ошибок парсинга TCP/TLS/QUIC, повторной сборки пакетов, checksum/sequence/fragment handling; нужно поддерживать драйвер и API; самостоятельная реализация методов не наследует проверенность zapret; размер/AV не обязательно уменьшаются, поскольку WinDivert driver остаётся. |

**Рекомендация: A для MVP, B только отдельными экспериментальными этапами после измерений.** Не портировать весь DPI-движок в Rust ради «одного exe»: драйвер всё равно остаётся отдельным системным компонентом, а узкое место — доказуемая совместимость и корректная обработка трафика, не язык. Упакованный single-exe может извлекать файлы в `%LOCALAPPDATA%`, но это всё равно поставка нескольких бинарников на диске. Требование размера ~15 MB пока не подтверждено: до реализации нужен инвентарь/размеры подписанного upstream release и измерение release-сборки.

## 3. Границы безопасности и Windows

- Повышение прав нужно лишь для запуска/установки драйвера и низкоуровневой фильтрации. Постоянный `requireAdministrator` означает elevated UI/tray и повышает последствия ошибок. Предпочтительнее обычный UI + минимальный привилегированный helper/service, но это усложняет поставку и cleanup. Это архитектурное решение требует явного одобрения.
- Не отключать Secure Boot, HVCI/Memory Integrity, Smart App Control, антивирус или политику подписи ради запуска. При блокировке драйвера завершаться с диагностикой и инструкцией; конкретную совместимость проверять на поддерживаемых сборках Windows и в VM.
- Windows Home не исключает службы/драйверы как класс, но допустимость конкретной установки зависит от версии ОС, подписи, security policy и прав; универсальную гарантию для всех Home конфигураций не заявлять.
- Конфликтующие перехватчики: другой `winws`, WinDivert-потребитель, VPN, firewall/AV и сетевые фильтры производителя. Перед запуском проверять только то, что можно обнаружить надёжно; не завершать неизвестные процессы автоматически.
- Покрытие IPv4/IPv6 должно быть явным в тестах. Списки IP и DNS/CDN адреса динамичны; IP-подбор кэша может устареть. QUIC/UDP блокировка часто требует отдельного теста и fallback браузера на TCP; автоматически менять системные настройки без сохранения и отката нельзя.
- Потеря питания, принудительное завершение процесса, падение системы или убийство elevated процесса обходят обычный cleanup. Гарантия «система всегда возвращается» невыполнима одной обработкой Ctrl+C/паники; нужны отдельный supervisor/service и безопасное восстановление состояния после следующего запуска.
- `requireAdministrator` вызывает UAC при каждом запуске (включая открытие из проводника); «один клик» означает подтверждение UAC пользователем. Автоматический доступ к YouTube без действий пользователя на первом запуске противоречит этому подтверждению.

## 4. Каталог, доставка и обновление

Встроенный в EXE подписанный/хешированный каталог TOML или JSON — источник истины для MVP, с `schema_version`, версией движка и происхождением каждого профиля. Парсер должен отвергать неизвестные критичные поля/флаги, плохие порты, traversal-пути и неверные хеши fake payload. Сетевое обновление каталога — только после верификации подписи ключом, зафиксированным в бинарнике; TLS и SHA-256 сами по себе не удостоверяют издателя. Атомарная запись новой версии, сохранение предыдущей и откат при невалидном каталоге обязательны. Несколько зеркал добавляют поверхность доверия; каждое зеркало должно поставлять один и тот же подписанный объект.

Файлы движка извлекать в каталог версии в `%LOCALAPPDATA%\ZapretA\` с проверкой фиксированных SHA-256 до запуска, ограниченными ACL, временным файлом и атомарным rename. DLL search path фиксировать на этот каталог. Не загружать исполняемые файлы/списки с произвольных URL. У каждой сетевой функции — документированный список доменов и отключаемая настройка обновлений; никаких фоновых передач диагностики.

## 5. Автоподбор: достижимый и проверяемый MVP

Разделить диагностику на фазы: (1) контрольная доступная цель + обычная DNS/TCP/TLS/HTTP; (2) DNS system vs DoH; (3) TLS/SNI цели; (4) UDP/QUIC только как дополнительный сигнал; (5) реальные HTTP-запросы к актуальным YouTube endpoints/CDN. Различие ответов DNS само по себе не доказывает подмену; таймаут/сброс не локализует DPI без контрольной цели и повторов. UDP `connect()` не подтверждает QUIC-доступность или успешную передачу данных. Для TLS SNI/HTTP нужен TLS-стек и корректный Host/SNI; нельзя подменять их голым TCP connect.

Классификатор сначала возвращает вероятностные признаки и уверенность, а не диагноз как факт. Если baseline показывает общую сетевую неисправность, не включать перехватчик. Последовательный перебор: lock единственного engine → запустить кандидата → дождаться готовности → одинаковый ограниченный test suite → остановить и подтвердить завершение → следующий профиль. Сохранять результаты, временные пределы, сетевой интерфейс, семейство IP и результаты control target; параллельные `winws` запрещены.

Score: жёсткий gate по контрольной цели и HTTP/TLS загрузке; затем доступность всех обязательных endpoints, скорость медиачанка (медиана нескольких проб, ограниченный объём), latency и стабильность повторов. Не выбирать победителя при провале повторной валидации. Кэш ключевать по хешу каталога + версии движка + сети/ASN, но не считать ASN надёжной идентичностью провайдера; быстрый путь всегда перепроверяет фактическую доступность. Watchdog не должен запускать перебор в бесконечном цикле: hysteresis, cooldown, лимит попыток, уведомление, ручной stop и безопасный rollback.

Открытие браузера и tray UI — постусловия после проверки: сначала открыть страницу только при подтверждённой доступности, показывать состояние «не проверено/работает/деградировало», не создавать ложное обещание, что YouTube доступен только по успешному TLS handshake.

## 6. Метрики и план проверки

- Unit: нормализация правил/argv, каталог schema/version, валидация путей и хешей, скоринг, кэш/инвалидация, конечный автомат процесса и cleanup.
- Integration: мок DNS/HTTPS и заведомо недоступная контрольная цель; сценарии таймаутов, reset, throttling, IPv4/IPv6, отказ драйвера, VPN/конфликтующий процесс; Windows VM snapshots для установки/остановки.
- MVP критерии измерять на конкретной матрице Windows build + сетевой провайдер/ASN + домашний роутер + security settings. Значения 60/10 секунд и 15 MB — целевые показатели, пока не доказанные характеристики.
- Exit: после нормального закрытия нет child process/driver; после аварийного завершения следующий запуск находит и безопасно снимает только собственный engine; чужие процессы не трогает. Логи без URL-параметров, аккаунтов, IP/SSID по умолчанию; `--diagnose` показывает, что именно будет включено в экспорт.

## Открытые вопросы до этапа 1

1. Какая лицензия/версия/хеши каждого бинарника Flowseal release и допустима ли перепаковка выбранных файлов? Проверить release assets и upstream licenses; текущая ветка репозитория сама по себе не источник бинарника.
2. Какой минимальный Windows build и какие подписи драйвера требуются для поддерживаемого WinDivert релиза при включённых Secure Boot/HVCI/SAC? Нужен тест в VM, не предположение.
3. Нужен ли Discord/Game Filter MVP? По целевому сценарию MVP — YouTube; остальное расширит поверхность тестирования и размер.
4. Как измерять «открытый рабочий YouTube» без браузерной автоматизации? HEAD/manifest/media chunk — неполная замена пользовательскому воспроизведению; критерий готовности следует формализовать.
5. Что означает «провайдер» в ключе кэша и как его определять без утечки? ASN может отсутствовать/меняться при VPN, мобильном интернете и CGNAT.
6. Автоматические обновления и мониторинг включены по умолчанию? Должны быть прозрачный список доменов, подпись metadata и ручное отключение.
7. Согласовать модель повышения прав: постоянно elevated приложение или разделение UI/service. Рекомендован второй вариант для сокращения времени работы с полными правами.
