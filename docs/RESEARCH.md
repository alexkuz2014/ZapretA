# Исследование источников ZapretA

Статус: исходное исследование этапа 0 завершено; реализация продолжается, 2026-10-30. Даты активности и лицензии нужно повторно проверить перед включением любых файлов в релиз.

## Реализация диагностического сетевого слоя

Следующий инкремент добавил в `zapreta-probe` типы `Known/Unknown`, DNS A/AAAA результаты и conservative-сигналы для пустого ответа, `0.0.0.0`, private/loopback/link-local адресов. Пустое семейство помечается как `Empty`, но общий DNS-сигнал остаётся `Unknown`: отсутствие AAAA может быть штатным. CLI формирует общий `BaselineReport`, разделяя контрольный example.com и target YouTube. HTTP-ответ любого статуса подтверждает TCP/TLS; не-2xx относится к HTTP/content результату, а сетевая ошибка оставляет фазы неизвестными.

Уточнение baseline: CLI получает системные адреса через untyped `lookup_host`; отсутствующее в объединённом списке семейство остаётся `NotRun`, а не успешным пустым A/AAAA ответом. DoH хранит отдельный результат запросов A и AAAA с состояниями `Answer`, `NoData`, `NxDomain` и `Incomplete` (например, незавершённая CNAME-цепочка). Только сетевые/HTTP/неподдерживаемые DNS ошибки запускают fallback. Сравнение использует нормализованные множества отдельно по семействам; разница RCODE/ответных состояний тоже отражается как возможное расхождение. Совпадающий private/loopback/unspecified ответ даёт отдельный `PossibleDnsSinkholeAnswer`; это эвристика, не доказательство подмены. System DNS API пока не раскрывает NODATA/NXDOMAIN отдельно, поэтому отсутствие семейства у него остаётся неизвестным.

Первый инкремент этапа 2 реализует ручную baseline-диагностику. Google документирует JSON API `https://dns.google/resolve`; Cloudflare предоставляет совместимый JSON API по `https://cloudflare-dns.com/dns-query`. Клиент пробует Google, затем Cloudflare при любой ошибке первого провайдера. Для обоих hostname заданы опубликованные IPv4 bootstrap IP (Google `8.8.8.8`, `8.8.4.4`; Cloudflare `1.1.1.1`, `1.0.0.1`) через reqwest `resolve_to_addrs`: URL сохраняет hostname для TLS SNI и проверки сертификата, но системный DNS не нужен для разрешения имени самого DoH-провайдера. IP являются настройкой, закреплённой в исходниках; при их изменении нужна проверка официальной документации и обновление тестов. Bootstrap сейчас использует IPv4, поэтому IPv6-only сеть не поддержана.

Google запросы содержат `edns_client_subnet=0.0.0.0/0`, Cloudflare запросы его не отправляют. Ни одна из мер не гарантирует анонимность: сетевые узлы видят соединение с выбранным резолвером, а проверочные цели получают HTTPS запросы. `zapreta-net` поддерживает локальные HTTP mock integration-тесты: проверяются переход на Cloudflare после HTTP 503 и невалидного JSON, A/AAAA запросы и ошибка, когда оба endpoint недоступны. Для HTTPS prober loopback тесты проверяют пустое, ровно лимитное и превышающее лимит тело, redirect без перехода, отказ соединения и timeout. Тестовый endpoint доступен только в `cfg(test)`; реальные внешние DNS/HTTPS запросы тестами не выполняются.

`reqwest` с rustls используется для прямых HTTPS запросов без proxy из окружения, без redirect и с таймаутом/ограничением чтения тела. Это только HTTP/TLS доступность, не проверка воспроизведения видео. На текущей машине сетевой запуск вернул HTTP 204 для YouTube и HTTP 200 для контрольного `example.com`; DNS-наборы различались наличием IPv6-адресов в DoH. Такие различия могут происходить из-за CDN и поддержки IPv4/IPv6, поэтому не классифицируются как доказанная подмена.

Источники: [Google Public DNS JSON API](https://developers.google.com/speed/public-dns/docs/doh/json), [официальные адреса Google Public DNS](https://developers.google.com/speed/public-dns/docs/using), [Cloudflare DoH JSON API](https://developers.cloudflare.com/1.1.1.1/encryption/dns-over-https/make-api-requests/), [адреса Cloudflare resolver](https://developers.cloudflare.com/1.1.1.1/infrastructure/network-operators/), [reqwest `resolve_to_addrs`](https://docs.rs/reqwest/0.12.28/reqwest/struct.ClientBuilder.html).

## Сверка каталога стратегий Flowseal

Для подготовки полного каталога получен архив ровно за source commit `176f56dc3f11ce5915c26abcdde903f93d835b64`; в нём обнаружено 22 `general*.bat`. `LICENSE.txt` этого среза заявляет MIT для кода и документации и отдельно указывает, что бинарные компоненты имеют собственное происхождение/лицензии. Только 22 текстовых профиля и `service.bat` помещены в `tests/fixtures/flowseal/` с upstream license; тесты читают их, никогда не исполняют. Engine-бинарники и payload-файлы не копировались.

Перед созданием catalog golden fixtures выявлено, что нынешние `Rule`/`strategy_argv` не могут представить все аргументы без потерь. В профилях присутствуют неподдерживаемые поля/варианты: `--filter-l3`, `--hostlist-domains`, `--hostlist-exclude-domains`, `--ip-id`, `--dpi-desync-any-protocol`, `--dpi-desync-fakedsplit-pattern`, `--dpi-desync-fake-tls-mod`, inline fake-значения без файлов, а также повторяющиеся payload-флаги разных типов. Некоторые скрипты используют `%GameFilterTCP%` / `%GameFilterUDP%`, которые в самих профилях не определены и зависят от окружения.

Добавлены 22 `catalog/flowseal/*.toml` как **неисполняемые source snapshots**. Каждый файл содержит нормализованный argv, исходный filename, SHA-256 скрипта и service, commit источника и defaults Game Filter. Golden-тест читает fixture batch, разбирает цепочку команд `winws.exe`, раскрывает `%BIN%`/`%LISTS%` и отключённые по умолчанию `%GameFilterTCP%`/`%GameFilterUDP%` в `12`, затем проверяет весь argv и SHA-256 для каждого из 22 профилей.

В runtime `Strategy` добавлен валидируемый `source_argv` для исходных профилей: он сохраняет повторяющиеся опции и порядок `--new`, проходит тот же allowlist/path validation, а `strategy_argv` возвращает только отдельные argv tokens без shell. Golden-тест импортирует каждый snapshot в `Strategy`, валидирует `StrategyCatalog` и сравнивает production `strategy_argv` со всеми токенами, извлечёнными из upstream batch для всех 22 профилей. Это обеспечивает точное представление исходных аргументов, но не подтверждает совместимость с конкретной версией движка. Профили не включены в каталог по умолчанию и не запускаются. Перед запуском всё ещё обязательны exact engine pin, payload SHA-256, лицензии и проверенный bundle.

Для `cargo deny` в список допустимых лицензий добавлена `CDLA-Permissive-2.0`, объявленная upstream crate `webpki-roots 1.0.11` (корневые сертификаты для TLS). Это явное разрешение лицензии зависимости, а не подтверждение лицензий будущих upstream executable/driver компонентов; их всё равно нужно разбирать отдельно.

## Вывод

На этом этапе надёжная фактическая база для каталога — только снимок исходных профилей Flowseal. Для MVP выбран предварительный оркестратор поверх закреплённого upstream engine (вариант A); выбор бинарного release и модель привилегий остаются открытыми до одобрения архитектуры и отдельной проверки лицензий/подписей.
